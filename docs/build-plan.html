The stack

One machine, and everything on it

Foundit runs on a single server you own, described entirely by files in this repository, so the worst case is rebuilding it in an hour rather than debugging it under pressure. The only usage-based bill is about a dollar a month, for the small model that reads the constraints out of your sentence.

The firewall you can watch lie to you

Docker publishes container ports through a different part of the kernel's firewall than ufw filters, and Docker's own rules run first. So a database can be open to the entire internet while ufw status reports, truthfully as far as it knows, that everything is blocked. This is how self-hosted databases end up publicly readable. It is guarded four separate ways, and the build is not finished until a scan from another network proves nothing is listening.

Where the research disagreed

Six rulings

Each report optimised for its own concern, so they collided. These are the calls, recorded so we don't relitigate them in three weeks. The first six settled the search; the last four settled the machine.

1
How much detail should each vector carry — 512 numbers or 1024?
512, shortened from a larger model. Keeps each row under the size where the database starts storing it the slow way: 20 MB instead of 123 MB. Retest at 1024 once there is a test set to judge it with.
2
Which company turns our text into vectors?
OpenAI, for now. We need an account there anyway for reading the query, and one supplier means one place to set a spending cap. Voyage has a generous free tier and is the first thing to try afterwards.
3
Add a reranker — the second pass that reorders the best 50 results?
Not in version one. It is probably the single biggest quality win available, which is exactly why it should not ship before we can measure it. It arrives in phase 5, with evidence.
4
Build a vector index to make search fast?
No. That kind of index quietly drops matches when results are filtered — and this product filters on nearly every search: free, offline, no account. At our size the honest, exhaustive scan is also the fast one.
5
Should the server open a submitted link to fill in the tool's details automatically?
Not in version one. A server that fetches any address a stranger names is a well-known way in, and checking the address beforehand does not fix it. Makers type their own name and summary; the auto-fill returns later, built properly. This is a change to the designed flow.
6
What do we keep from a search?
A fingerprint of the query, never the words next to a name. "Describe your problem" collects health, money and relationship troubles. Counts tell us what people need; transcripts are a liability.
7
Run the Supabase stack on our own machine, or plain PostgreSQL?
Plain PostgreSQL, with Better Auth. The Supabase stack is thirteen services, and its one unique gift was telling the database who the current user is — about twenty lines of code. Every container is something that breaks at 3am in front of someone who is not a developer.
8
Firewall the server's public address, or open no ports at all?
No ports at all. The server dials out to Cloudflare and traffic returns down that pipe, so there is nothing on the internet to scan or attack — and no published port for Docker to expose past the firewall.
9
One machine, or one for production and one for development?
One, with a written trigger to split: a second person getting access, or development work visibly slowing the live site. The honest cost is that big changes — a database version upgrade, a kernel update — can never be rehearsed first.
10
How much downtime is acceptable when deploying?
Two to ten seconds, hidden by the proxy retrying. Eliminating it entirely on four cores costs more than it returns.

Search quality

Three things decide whether it works

Everything else in the pipeline is adjustable. These three are the product.

  • Store the problems a tool solves, written as sentences — not its marketing copy. This is the highest-leverage decision in the whole system. A page that says "delightful, powerful, intuitive" matches nothing anyone would ever type.
  • Constraints are a filter, never a hint. If someone says free, a paid tool does not appear, however similar it looks. "Free" must never be a vibe.
  • Sixty test queries with known right answers, written before any tuning. Without them, every later change is a guess dressed as an improvement. With them, each upgrade is settled in an afternoon.

The fit score has to earn its number

Until there are enough judged examples to calibrate it, results show a band — Strong, Possible, Loose — not a percentage. A similarity figure rescaled to look like "92% fit" is a lie, and people can feel it when the 92% is wrong.

Safety rails

The search page is public, needs no account, and calls a paid model on every miss. That is precisely the shape someone points a script at, so the app's own limits matter as much as the suppliers' caps.

Security gates before launch

The database is the real boundary: rules inside PostgreSQL decide who may read and write each row, so an application bug cannot become a data breach. Self-hosted, that boundary breaks silently in three ways, and each has an automatic check:

  • The app connects as the table's owner. The rules are all still there, the tests still pass, and nothing is enforced — owners bypass their own tables' rules.
  • A request's identity leaks into the next request through a reused database connection, so one person is served as another. It never reproduces in testing, because testing is not concurrent.
  • A table added later never gets its rules switched on. The only one of the three that fails open.

Plus the unchanging two: no rule anywhere evaluates to "always allow", and no secret appears in any built file or any commit, ever.

The most likely breach is not an attacker

It is an assistant — me, or any other — hitting a permissions error and "fixing" it by switching the row rules off or reaching for the master key. Both are forbidden on this project, and both are checked automatically on every change.

Backups are now entirely ours

The database ships its changes continuously to Cloudflare R2 — a different company from the one hosting the server, because off-site has to mean off-provider. Worst case is losing five minutes, not a day. A separate encrypted dump runs nightly, because two mechanisms fail independently.

And once a week a job restores the whole thing from scratch, counts the rows, runs a real search against it, and only then reports success. Silence is the alarm. A backup nobody has restored is not a backup.

Build order

Eight phases, each one shippable

Phases 2 through 5 each end by scoring the same sixty queries. If a change doesn't move the score, it doesn't ship — that rule is what keeps this from becoming a pile of plausible-looking machinery.

  1. Phase 0
    The domainYouDone
    Bought, and its DNS moved to Cloudflare before the machine exists — because the first time a domain resolves to a raw server address, that pairing is public forever and the protection is undone.
  2. Phase 0b
    The machine, built onceYouMe
    A key made and backed up, the firewall created before the server, a non-root user proved in a second terminal before anything is locked, password logins off, Docker configured so containers cannot publish to the world, automatic security updates, the tunnel, and the backup job. Finished only when a scan from another network finds nothing listening.
  3. Phase 1
    The databaseMe
    Tables as migration files, row rules switched on in the very first one, invented data for development. Nothing clicked into a dashboard, ever.
  4. Phase 2
    Search with no AI in itMeThe baseline
    Plain text search plus constraint filtering. The sixty test queries get written here, along with the script that scores them. Everything after this has to beat it.
  5. Phase 3
    VectorsMe
    Embeddings, and the fusion of text and vector results into one ranking. Measured against phase 2.
  6. Phase 4
    Understanding the sentenceMe
    Pulling "free", "offline", "in Spanish" out of the query, and restating a non-English query in English for matching. Measured.
  7. Phase 5
    Better rankingMe
    Generated problem statements, then the reranker, then a real fit percentage replacing the bands. Each one measured on its own so we know which earned its place.
  8. Phase 6
    AccountsMe
    Sign-in, saving, likes, reviews. Written rules-first: what the database permits goes in before the screens that use it.
  9. Phase 7
    Adding a toolMe
    The submit flow, the maker dashboard, and claiming a listing we seeded at launch.
  10. Phase 8
    HardeningMeLaunch gate
    Rate limits, the backup job and a restore we have actually run, error reporting, page speed, and the security checklist top to bottom.

Still unknown

What the research could not confirm

About sixty claims across the six reports are marked unverified. Four could change a decision:

  • The speed of the outside model calls is an estimate, not a published figure — and those calls dominate a search. Measure on day one.
  • Whether generated problem statements really beat plain descriptions is unproven for this kind of search. The test set settles it in an afternoon.
  • What the server actually costs. Hetzner raised cloud prices by a third to more than double on 15 June 2026, and renders prices in JavaScript, so no figure I have is trustworthy until you read it from their console.
  • None of the database code in the reports has ever been run. It is a starting point to execute and fix, not to trust.
